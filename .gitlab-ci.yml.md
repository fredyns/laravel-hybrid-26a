# Petunjuk `.gitlab-ci.yml`

Dokumen ini menjelaskan isi file [`.gitlab-ci.yml`](.gitlab-ci.yml) untuk pembaca
yang **baru pertama kali memakai GitLab CI/CD**. Dibaca berurutan dari atas.

Dokumen pendamping: [`deployment/env/staging/README.md`](deployment/env/staging/README.md)
— cara mengisi secrets. Dokumen ini fokus pada cara kerja pipeline-nya.

---

## 1. Konsep dasar

Setiap kali Anda `git push`, GitLab membaca file `.gitlab-ci.yml` di root
repository, lalu menjalankan perintah-perintah yang tertulis di sana pada
komputer lain (bukan laptop Anda).

| Istilah | Artinya |
|---|---|
| **Runner** | Mesin milik GitLab yang menjalankan perintah Anda |
| **Pipeline** | Sekumpulan pekerjaan yang jalan untuk satu commit |
| **Stage** | Tahap/babak dalam pipeline. Stage berjalan berurutan |
| **Job** | Satu pekerjaan konkret. Job dalam stage yang sama jalan bersamaan |
| **Image** | Docker image tempat job dijalankan, misal `php:8.5-cli-alpine` |
| **Script** | Daftar perintah shell yang dijalankan job |
| **Artifact** | File hasil job yang diwariskan ke job berikutnya |
| **Cache** | Folder yang disimpan antar-pipeline supaya tidak download ulang |
| **Variable** | Nilai yang disimpan di GitLab (bukan di kode), untuk secrets |
| **Environment** | Catatan "versi mana yang sedang jalan di server mana" |

Poin penting bagi pemula: **setiap job mulai dari nol.** Job berikutnya tidak
otomatis melihat hasil job sebelumnya. Kalau butuh hasilnya, harus lewat
`artifacts` atau `cache`.

---

## 2. Gambaran pipeline project ini

```
stage:  build            test              deploy                 verify
        ─────────────    ──────────────    ───────────────────    ─────────────────────
        build:vendor  →  test:lint      →  deploy:staging:code →  verify:staging:containers
        build:assets     test:types        deploy:staging:        verify:staging:routes (manual)
                         test:pest         containers (manual)    maintenance:staging:git-remote (manual)
```

Alurnya: siapkan dependency → periksa kualitas kode → kirim ke server staging →
periksa hasilnya. Kalau tahap `test` gagal, tahap `deploy` **tidak dijalankan**.

## 3. Bedah file, bagian per bagian

### 3.1 `stages` (baris 6–10)

```yaml
stages:
  - build
  - test
  - deploy
  - verify
```

Ini urutan babaknya. Semua job di `build` harus selesai sebelum `test` mulai,
dan seterusnya.

Perhatikan penamaannya: **stage diberi nama sesuai tahapan, bukan sesuai server.**
Jadi bukan `staging_pull` atau `prod_container`. Kenapa? Karena kalau nanti
menambah server produksi, Anda cukup menambah *job* baru di stage `deploy` yang
sudah ada — tidak perlu menambah stage baru. Nama servernya ditulis di nama job
(`deploy:staging:code`) dan di bagian `environment:`.

### 3.2 `variables` (baris 12–16)

Variabel yang berlaku untuk semua job. Di sini isinya bukan rahasia, hanya
pengaturan teknis:

- `GIT_DEPTH: "20"` — runner cukup mengambil 20 commit terakhir, bukan seluruh
  sejarah repo. Lebih cepat.
- `COMPOSER_CACHE_DIR` / `npm_config_cache` — mengarahkan folder cache ke dalam
  direktori project supaya bisa disimpan oleh `cache:`.

Secrets **tidak boleh** ditulis di sini. Secrets diisi lewat
Settings → CI/CD → Variables.

### 3.3 `workflow` (baris 19–24)

```yaml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH
```

Ini mengatur **kapan pipeline dibuat sama sekali**. Dibaca dari atas, aturan
pertama yang cocok yang dipakai:

1. Kalau ini merge request → jalan.
2. Kalau ini push ke branch yang **sedang punya MR terbuka** → jangan jalan
   (karena aturan no. 1 sudah menanganinya). Tanpa baris ini, satu commit bisa
   memicu dua pipeline sekaligus dan menghabiskan kuota.
3. Selain itu, kalau ada branch → jalan.

> **Catatan:** aturan di atas tidak menyebut tag sama sekali, jadi `git push --tags`
> **tidak** memicu pipeline. Ini penting kalau nanti Anda ingin deploy berbasis
> tag — lihat bagian 5.2.

### 3.4 `default` (baris 26–32)

Setelan bawaan untuk semua job:

- `interruptible: true` — kalau ada push baru, pipeline lama boleh dibatalkan
  otomatis. Hemat runner. (Job deploy mematikan opsi ini, lihat 3.8.)
- `retry` — ulangi otomatis maksimal 2× **hanya** kalau penyebabnya masalah
  runner/timeout, bukan karena kode Anda gagal test.

### 3.5 Template: job yang diawali titik (baris 40–79)

Job yang namanya diawali titik, seperti `.php`, tidak pernah dijalankan. Ia hanya
cetakan untuk dipakai ulang lewat `extends:`.

```yaml
.php:
  image: php:8.5-cli-alpine
  before_script:
    - apk add --no-cache git unzip libzip
    ...

test:lint:
  extends: .php      # <— mewarisi image + before_script di atas
  stage: test
  script:
    - composer lint:check
```

Ada empat template di file ini:

| Template | Isinya |
|---|---|
| `.php` | Image PHP 8.5 + pasang ekstensi + install Composer + login Flux Pro |
| `.node` | Image Node 22 untuk build asset |
| `.ssh_staging` | Menyiapkan koneksi SSH ke server staging |
| `.staging_only` | Aturan "job ini hanya jalan di branch utama" |

Kenapa `.node` memakai `node:22-bookworm-slim` dan bukan versi Alpine? Karena
`package.json` mengunci paket `*-linux-x64-gnu` yang tidak jalan di Alpine (musl).

### 3.6 `.ssh_staging` dan kunci SSH (baris 57–75)

```yaml
    - printf '%s\n' "$SSH_PRIVATE_KEY_STAGING" | tr -d '\r' | ssh-add -
```

Private key **tidak ditulis ke file**, langsung dimasukkan ke `ssh-agent`.
`tr -d '\r'` membuang karakter Windows line ending yang sering terbawa saat
menempel key ke kolom variable.

Bagian `known_hosts` memastikan runner benar-benar bicara dengan server yang
benar. Kalau variable `SSH_KNOWN_HOSTS_STAGING` belum diisi, job tetap jalan tapi
mencetak peringatan — sebaiknya segera diisi dengan hasil `ssh-keyscan -H <host>`.

### 3.7 Anchor YAML `&` dan `*` (baris 92–109)

```yaml
.push_staging_env: &push_staging_env
  - |
    if [ -z "$STAGING_ENV_FILE" ]; then ... fi
    scp -q "$STAGING_ENV_FILE" "$SSH_TARGET:${APP_PATH}/.env"
```

lalu dipakai di job:

```yaml
  script:
    - ssh ... < deployment/scripts/git_pull.sh
    - *push_staging_env          # <— disalin ke sini
    - ssh ... < deployment/env/staging/deploy_code.sh
```

`&nama` = "beri label pada blok ini". `*nama` = "tempelkan blok berlabel itu di
sini". Bedanya dengan `extends`: `extends` untuk mewarisi **seluruh job**,
anchor untuk menyisipkan **potongan** di tengah daftar `script`.

Blok ini menyalin file environment dari GitLab ke server. Urutannya penting:
harus **setelah** clone/pull, karena job rebuild menghapus seluruh folder aplikasi
lebih dulu.

### 3.8 Job `build` dan beda cache vs artifacts (baris 116–147)

```yaml
build:vendor:
  cache:                      # dipakai ulang antar-pipeline (mempercepat)
    key:
      files: [composer.lock]
    paths: [.cache/composer]
  script:
    - composer install --prefer-dist --no-progress --optimize-autoloader
  artifacts:                  # diwariskan ke job berikutnya dalam pipeline ini
    expire_in: 1 hour
    paths: [vendor/]
```

Perbedaan yang sering membingungkan pemula:

| | Cache | Artifacts |
|---|---|---|
| Tujuan | Mempercepat | Mengoper hasil kerja |
| Hidup | Antar-pipeline | Dalam satu pipeline |
| Contoh | File unduhan Composer | Folder `vendor/`, `public/build/` |

`key: files: [composer.lock]` artinya cache diperbarui hanya saat isi
`composer.lock` berubah.

### 3.9 Job `test` dan `needs` (baris 154–177)

```yaml
test:lint:
  needs: [build:vendor]
```

Secara default job menunggu **seluruh stage sebelumnya** selesai. `needs:`
memotong antrean: `test:lint` cukup menunggu `build:vendor`, tidak perlu
menunggu `build:assets`. Ini yang disebut pipeline DAG dan membuat total waktu
lebih singkat.

`test:pest` butuh keduanya, karena test Laravel merender view yang memakai
`@vite` — jadi butuh hasil build asset.

### 3.10 Job `deploy` (baris 187–226)

```yaml
deploy:staging:code:
  extends:
    - .ssh_staging
    - .staging_only
  needs: [test:lint, test:types, test:pest]
  interruptible: false
  resource_group: staging
  timeout: 20 minutes
  environment:
    name: staging
    url: "$APP_URL"
    deployment_tier: staging
```

Yang perlu dipahami:

- `needs:` ke tiga job test → **kode yang gagal test tidak akan sampai ke server.**
- `interruptible: false` → deploy yang sedang berjalan tidak boleh dibatalkan di
  tengah jalan oleh push baru.
- `resource_group: staging` → GitLab mengantre job dengan grup sama. Dua pipeline
  tidak bisa deploy bersamaan dan saling menimpa.
- `environment:` → muncul di menu **Deployments → Environments**, lengkap dengan
  tombol ke `url` dan riwayat versi yang pernah dideploy.

Job `deploy:staging:containers` dibedakan karena sifatnya merusak: ia menghapus
folder aplikasi, clone ulang, lalu build ulang semua container. Karena itu ia
`when: manual` — harus diklik manual di UI GitLab.

### 3.11 `rules` (pengganti `only`)

```yaml
rules:
  - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    when: manual
    allow_failure: false
```

`only:` adalah gaya lama dan sudah tidak dianjurkan. `rules:` lebih jelas dan
bisa menggabungkan syarat + `when` + `allow_failure` sekaligus.

`allow_failure: false` pada job manual berarti: selama job ini belum diklik dan
sukses, pipeline dianggap belum selesai. Kalau `true`, pipeline tetap dianggap
hijau meski job dilewati.

### 3.12 Stage `verify` dan `maintenance` (baris 233–277)

Job pemeriksaan setelah deploy (lihat container, lihat daftar route). Sifatnya
hanya membaca. `maintenance:staging:git-remote` dipisah namanya karena ia
**menulis** (mengubah remote git di server) — jangan dicampur dengan job yang
sekadar memeriksa, supaya tidak terklik tanpa sengaja.

## 4. Variabel yang harus ada di GitLab

Settings → CI/CD → Variables. Detail pengisian ada di
[`deployment/env/staging/README.md`](deployment/env/staging/README.md).

| Variable | Kegunaan |
|---|---|
| `STAGING_ENV_FILE` | Isi file `.env` staging (tipe **File**) |
| `SSH_PRIVATE_KEY_STAGING` | Private key ke server staging |
| `SSH_USER_STAGING`, `SSH_STAGING` | User dan host server |
| `SSH_KNOWN_HOSTS_STAGING` | Sidik jari host, hasil `ssh-keyscan -H <host>` |
| `token_pull` | Token GitLab untuk clone/pull di server |
| `APP_URL` | Alamat staging, dipakai link environment |
| `FLUX_USERNAME`, `FLUX_LICENSE_KEY` | Lisensi Flux Pro untuk `composer install` |

## 5. Variasi

### 5.1 Menambah deploy ke server produksi

Prinsipnya: **tambah job, jangan tambah stage.** Semua stage yang dibutuhkan
(`deploy`, `verify`) sudah ada.

**Langkah 1 — siapkan file di repo.** Salin folder staging sebagai contoh:

```bash
cp -r deployment/env/staging deployment/env/production
```

Lalu di dalam `deployment/env/production/`, sesuaikan `docker-compose.yml`,
`deploy_code.sh`, `deploy_container.sh`, dan `.env.example` untuk produksi.

**Langkah 2 — tambah variable di GitLab:**

| Variable | Tipe | Protect |
|---|---|---|
| `PRODUCTION_ENV_FILE` | File | ✅ |
| `SSH_PRIVATE_KEY_PRODUCTION` | Var | ✅ |
| `SSH_USER_PRODUCTION`, `SSH_PRODUCTION` | Var | ✅ |
| `SSH_KNOWN_HOSTS_PRODUCTION` | Var | ✅ |
| `APP_URL_PRODUCTION` | Var | ✅ |

**Langkah 3 — tambahkan ke `.gitlab-ci.yml`:**

```yaml
# --- template SSH produksi (sejajar dengan .ssh_staging) ---
.ssh_production:
  image: alpine:3.21
  variables:
    SSH_TARGET: "${SSH_USER_PRODUCTION}@${SSH_PRODUCTION}"
  before_script:
    - apk add --no-cache openssh-client
    - eval "$(ssh-agent -s)"
    - printf '%s\n' "$SSH_PRIVATE_KEY_PRODUCTION" | tr -d '\r' | ssh-add -
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh
    - printf '%s\n' "$SSH_KNOWN_HOSTS_PRODUCTION" > ~/.ssh/known_hosts
    - chmod 600 ~/.ssh/known_hosts

# --- pengiriman file environment produksi ---
.push_production_env: &push_production_env
  - |
    if [ -z "$PRODUCTION_ENV_FILE" ]; then
      echo "ERROR: variable PRODUCTION_ENV_FILE belum diisi."
      exit 1
    fi
    APP_PATH="/home/administrator/${CI_PROJECT_NAME}"
    scp -q "$PRODUCTION_ENV_FILE" "$SSH_TARGET:${APP_PATH}/.env"
    ssh "$SSH_TARGET" "cd ${APP_PATH} && chmod 640 .env && (chown 1000:1000 .env || true)"

# --- job deploy produksi ---
deploy:production:code:
  extends: .ssh_production
  stage: deploy
  needs: [test:lint, test:types, test:pest]
  interruptible: false
  resource_group: production          # antre sendiri, terpisah dari staging
  timeout: 30 minutes
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual                    # produksi selalu manual
      allow_failure: false
  script:
    - ssh "$SSH_TARGET" "CI_PROJECT_NAME='$CI_PROJECT_NAME' CI_PROJECT_PATH='$CI_PROJECT_PATH' token_pull='$token_pull' bash -s" < deployment/scripts/git_pull.sh
    - *push_production_env
    - ssh "$SSH_TARGET" "CI_PROJECT_NAME='$CI_PROJECT_NAME' CI_PROJECT_PATH='$CI_PROJECT_PATH' token_pull='$token_pull' bash -s" < deployment/env/production/deploy_code.sh
  environment:
    name: production
    url: "$APP_URL_PRODUCTION"
    deployment_tier: production
```

**Tiga hal yang wajib diperhatikan:**

1. **`when: manual`.** Produksi jangan pernah otomatis. Beri jeda manusia.
2. **`resource_group: production` terpisah** dari staging, supaya deploy staging
   tidak menahan antrean produksi.
3. **Script di `deployment/scripts/` masih menuliskan path dan nama container
   secara tetap** (`/home/administrator/...`, `laravelkit26_app`). Kalau produksi
   berada di server yang berbeda, ini aman. Tapi kalau staging dan produksi ada
   di **satu server yang sama**, nama container akan bentrok — path dan nama
   container harus dijadikan variabel lebih dulu.

### 5.2 Deploy produksi berbasis tag (rilis)

Kalau ingin produksi dideploy dari tag `v1.2.3`, bukan dari branch:

```yaml
# 1) izinkan pipeline berjalan saat ada tag
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_TAG              # <— tambahan
    - if: $CI_COMMIT_BRANCH

# 2) ganti rules pada job produksi
deploy:production:code:
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual
      allow_failure: false
```

Tanpa tambahan pada `workflow.rules`, `git push --tags` tidak akan memicu
pipeline sama sekali sehingga job produksi tak pernah muncul.

### 5.3 Menambah job SonarQube

Pola dari project lain di organisasi ini:

```yaml
sonarqube-check:
  stage: test
  image: sonarsource/sonar-scanner-cli:latest
  tags:
    - shared-docker-executor      # arahkan ke runner tertentu
  needs: []                       # tidak menunggu job lain
  variables:
    SONAR_USER_HOME: "${CI_PROJECT_DIR}/.sonar"
    SONAR_HOST_URL: "$SONAR_HOST_URL"
    SONAR_TOKEN: "$SONAR_TOKEN"
  script:
    - sonar-scanner
  allow_failure: true             # laporan mutu, jangan menahan deploy dulu
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

`tags:` dipakai kalau organisasi punya beberapa runner dan job harus jalan di
runner tertentu.

### 5.4 Menjalankan pipeline terjadwal

**Build → Pipeline schedules → New schedule.** Berguna untuk backup atau
pemeriksaan rutin. Job yang hanya untuk jadwal dibatasi dengan:

```yaml
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
```

## 6. Kalau pipeline gagal

1. Buka **Build → Pipelines**, klik job yang merah, baca log dari **bawah**.
2. Gagal di `test:lint` → jalankan `composer lint` lokal, commit hasilnya.
3. Gagal di `test:types` → jalankan `composer types:check` lokal.
4. Gagal di `test:pest` → jalankan `php artisan test --compact` lokal.
5. Gagal di `build:vendor` dengan error autentikasi → `FLUX_USERNAME` /
   `FLUX_LICENSE_KEY` belum diisi atau salah.
6. Gagal di `deploy:*` dengan `Permission denied (publickey)` → key SSH salah,
   atau variable-nya di-**protect** sementara branch Anda belum protected.
7. Gagal dengan `STAGING_ENV_FILE is not set` → variable belum dibuat, atau
   dibuat sebagai Protected padahal branch belum di-protect.

Perbaiki penyebabnya, lalu klik **Retry** pada job tersebut — tidak perlu
mengulang seluruh pipeline.

---

## 7. Aturan main

- Jangan pernah menulis password/token langsung di `.gitlab-ci.yml`. File ini
  ikut ter-commit dan bisa dibaca semua orang yang punya akses repo.
- Jangan `echo` atau `cat` isi file environment di dalam job. Log job bisa dibaca
  semua Developer.
- Setiap job berjalan di mesin bersih. Kalau butuh hasil job lain, pakai
  `artifacts` + `needs`.
- Ubah pipeline lewat merge request supaya bisa direview — pipeline juga kode.
